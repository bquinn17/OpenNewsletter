# Frontend architecture

How the SPA is built, routed, and shipped: React 18 + TypeScript + Vite + Tailwind, deployed as static assets to GitHub Pages on a custom domain. Mobile-first, constrained to the middle third on desktop. Progressive Web App with an installable manifest, a service worker, and Web Push. Read this alongside [`api.md`](api.md) for the wire shapes the frontend consumes and [`auth.md`](auth.md) for the OIDC flow; `frontend/src/types/api.ts` (generated from `shared/openapi.yaml`) is the source of truth for API types, and the code under `frontend/src/` is the source of truth for everything else here.

## 3. Routing

React Router v6 (`createBrowserRouter`). Pages fetch through TanStack Query hooks (`useNewsletter` etc.), not route loaders.

```
/                           Home (newsletter list across all my groups)
/auth/callback              OIDC callback
/join                       Invite redemption (?code=...)
/settings                   User settings + push subscription
/g/:groupId                 Redirects to most recent newsletter
/g/:groupId/upcoming        Candidate questions (vote + suggest)
/g/:groupId/upcoming/suggest    New candidate form
/g/:groupId/n/:cycleId      Newsletter view (voting/open/published states render different UIs)
/g/:groupId/n/:cycleId/respond/:questionId   Editor for one question
/g/:groupId/admin           Admin page (gated by role) — Members / Invites / Settings tabs only (no Curate; see lifecycle.md §7)
/admin/bootstrap-login      Dev-only username/password login against the `admin-bootstrap` Cognito client; hidden in prod via `env.appEnv !== "dev"` (see `docs/development/environments.md` §6)
*                           NotFound
```

Route guards:
- All routes except `/auth/callback`, `/join`, and `/` redirect to OIDC login if no valid token.
- `/g/:groupId/*` checks membership (`RequireMembership`); not a member → redirect to `/`.
- `/g/:groupId/admin` checks `role === 'admin'` (`RequireGroupAdmin`); otherwise → redirect to group home.
- Both guards read the cached `/config` (`staleTime: Infinity`). Before denying, they refetch once (`routes/useConfirmedAccess.ts`), so a membership or role granted elsewhere, such as another tab or a just-redeemed invite, isn't bounced.

## 4. Layout

### 4.1 Shell

```
┌─ AppShell ─────────────────────────────────────────────────┐
│  Header (sticky)                                            │
│   - Logo + group switcher (left)                            │
│   - Cycle status pill (center)                              │
│   - Avatar + menu (right)                                   │
├────────────────────────────────────────────────────────────┤
│  Main content                                               │
│   - Mobile: full width, padding-x: 16px                     │
│   - ≥md: max-w-3xl mx-auto (middle third effectively)       │
│   - ≥lg: max-w-2xl mx-auto                                  │
└────────────────────────────────────────────────────────────┘
```

There is no bottom tab bar. Navigation is the header: the logo goes Home, the group switcher picks the group Home shows, and the avatar menu holds Settings. Home's edition rows lead to the open edition (respond) and the voting cycle (Upcoming). A mobile `BottomNav` existed until 2026-10-14; it was removed because it duplicated Home and covered RespondPage's own bottom bar ([`decisions.md`](../decisions.md#home-shows-one-group)).

The current group (`state/currentGroup.ts`, persisted) is set by the switcher, defaults to the first membership, and follows the URL: opening any `/g/:groupId/*` page makes that group current, so a deep link from a push notification or shared link doesn't leave Home showing a different group. Picking a group in the switcher navigates to Home.

Tailwind container choice: stick with `max-w-2xl` on large screens. The "middle third" requirement from the spec is achieved by capping width rather than using a 3-column grid — simpler, more legible, same visual outcome.

### 4.2 Theming

CSS variables on `:root` for `--bg`, `--surface`, `--text`, `--text-muted`, `--accent`, `--border`. Tailwind extended with these via `theme.extend.colors`. Dark mode: driven by `prefers-color-scheme` only. A user-facing toggle is not built.

### 4.3 Typography

Fonts: Plus Jakarta Sans and Fraunces from Google Fonts (§12.1). Body 16px, line-height 1.55. Markdown is styled by a small hand-written prose ruleset in `styles/tailwind.css`; `@tailwindcss/typography` isn't used.

### 5.2 Service worker / caching strategy

Workbox config (via plugin):

- **Precache**: Vite-built static assets (JS/CSS/HTML).
- **Runtime caches**:
  - Media images, cache name `media-images`: matches the media origin's `/img/*` paths ([`media.md` §4.4](media.md#44-spa-usage)). `CacheFirst`, 200-only, `expiration: { maxEntries: 200, maxAgeSeconds: 30 days }`. Avatars (`/avatar/*`) get the same route in their own cache, `media-avatars`, with `maxAgeSeconds: 90 days` ([`media.md` §11.3](media.md#113-serving)). The origin is the processed S3 bucket (`VITE_MEDIA_BASE_URL`, §13), and the URL is a presigned GET whose query string changes every signing window, so the cache key is origin + path with the query stripped (`swHelpers.mediaCacheKey`), or entries would churn on every re-sign even though the underlying object hasn't changed. **CORS mode:** `MediaImage` and `Avatar` render `crossorigin="anonymous"` (the signature lives in the URL, so no credentials are needed), and the processed bucket answers with plain (non-credentialed) CORS for the SPA's origins ([`infrastructure.md` §5.1](infrastructure.md#51-s3-buckets-mediapersistentstack)). A plain cross-origin `<img>` gives the service worker an opaque status-0 response, which `CacheFirst` won't store, and which would pin a 403 if it did. In CORS mode it sees the real status, so only 200s are cached. Every media `<img>` must use the same mode: a copy cached in one mode fails a request made in the other.
  - **API GETs are not cached.** Authenticated API responses in Cache Storage would be keyed by URL, not by user, and would outlive logout — a second user on a shared device could be served the first user's data offline. The SW does not touch API requests at all (so `/config` and tokens are network-only by construction). Revisit with per-user cache names cleared on logout if offline reads are wanted.
- **Update activation:** the SW activates a new version promptly rather than waiting for every tab to close, because backend and frontend promote together from one SHA ([D6](../decisions.md#d6)) and an installed PWA needs to pick up the matching frontend quickly. `VitePWA` runs with `registerType: "autoUpdate"` (or explicit `skipWaiting()` + `clients.claim()` in `sw.ts`), and `registerSW({ immediate: true })` in `main.tsx` (§14.2) checks for updates on load. A client picks up the new version on its next load/navigation, not mid-session. (As built, §14.2 below.)

### 5.3 Push subscription flow

`pwa/pushSetup.ts` (sketch; the real signature is `ensurePushSubscription(vapidPublicKey, { prompt })`, which never prompts when `prompt` is false and replaces a subscription made with a different VAPID key — [`notifications.md` §11.2](notifications.md#112-re-subscribe-on-load)):

```ts
export async function ensurePushSubscription(vapidPublicKey: string) {
  if (Notification.permission === "denied") return;
  if (Notification.permission !== "granted") {
    const result = await Notification.requestPermission();
    if (result !== "granted") return;
  }
  const reg = await navigator.serviceWorker.ready;
  const existing = await reg.pushManager.getSubscription();
  const sub = existing ?? await reg.pushManager.subscribe({
    userVisibleOnly: true,
    applicationServerKey: urlB64ToUint8Array(vapidPublicKey),
  });
  await api.push.subscribe(sub.toJSON());
}
```

Triggered:
- On settings page when user toggles "Push notifications" on
- Re-sent on app load if a subscription already exists (keeps server's `lastSuccessAt` ticking and reattaches dropped subs)

### 5.4 SW push handler

In a custom SW (`src/pwa/sw.ts`) injected into the Workbox SW:

```ts
self.addEventListener("push", (event) => {
  const data = event.data?.json() ?? {};
  event.waitUntil(self.registration.showNotification(data.title ?? "OpenNewsletter", {
    body: data.body,
    icon: "/icon-192.png",
    badge: "/icon-192.png",
    data: { url: data.url },
    tag: data.tag,
  }));
});

self.addEventListener("notificationclick", (event) => {
  event.notification.close();
  const url = event.notification.data?.url ?? "/";
  event.waitUntil((async () => {
    const all = await self.clients.matchAll({ type: "window" });
    const focused = all.find((c) => c.url.startsWith(url));
    if (focused) return focused.focus();
    return self.clients.openWindow(url);
  })());
});
```

Push payloads from backend documented in [`notifications.md` §5](notifications.md#5-push-payload-schema).

## 6. Auth in the SPA

See [`auth.md`](auth.md) for the full sequence. The frontend pieces:

- `auth/AuthProvider.tsx` `login()` — initiates the Cognito hosted UI redirect with PKCE. If a `?code=` invite param is present in the URL when login starts, `{ invite, returnTo }` rides along as `oidc-client-ts`'s `signinRedirect({ state })` data so it survives the OAuth round-trip: the library keeps that data in its client-side state store keyed by the opaque OIDC `state` value, which stays a pure CSRF nonce — nothing user-controlled travels through Cognito. The code is also stashed in `sessionStorage` as a fallback. The `PreSignUp` trigger never sees it — redemption happens after token exchange via `POST /invites/redeem` ([`auth.md` §3](auth.md#3-presignup-lambda)–§4).
- `pages/AuthCallbackPage.tsx` — exchanges `code` for tokens (once, StrictMode-safe), stores them, and redirects to the original page, or to `/join?code=…` when an invite rode along.
- `auth/userManager.ts` — stores tokens in `localStorage` (moved from `sessionStorage` so an installed PWA stays signed in across launches; refresh token lifetime 30 days). Renewal is `auth/renewSession.ts`, run on `accessTokenExpiring`, on a reload with an expired ID token, and on a 401. Federated sessions use `oidc-client-ts`'s **refresh-token grant**; Cognito has no `prompt=none` iframe flow. Bootstrap-login sessions, recognised by the ID token's `aud`, use Cognito `REFRESH_TOKEN_AUTH` against the `admin-bootstrap` client instead. `automaticSilentRenew` is off, because it would route bootstrap sessions through the wrong client and sign them out.
  - **Threat model:** full writeup in [`auth.md` §12](auth.md#12-threat-model-considerations). In short, XSS exposure is the same regardless of storage; the difference `localStorage` makes is a stolen refresh token's lifetime (up to 30 days unless revoked). CSP (§12.1) and logout's revoke call are the mitigations; shared-device residue is accepted as-is ([D9](../decisions.md#d9)).
- `auth/AuthProvider.tsx` — Context exposing `{ status, user, login, logout }` via `useAuth()`. Wraps the app, inside `QueryClientProvider`. **Logout** removes the stored user from `localStorage`, clears the TanStack Query cache and persisted Zustand stores (`currentGroup`, etc.), best-effort revokes the refresh token via Cognito `POST /oauth2/revoke`, then redirects to Cognito `/logout`.
- `auth/RequireAuth.tsx` — layout-route guard for §3's protected routes.
- `api/client.ts` — adds `Authorization: Bearer ${idToken}` (the **ID token**, [`api.md` §1](api.md#1-general-conventions)) and `x-correlation-id`; on a 401 it tries one silent renew and retries once.
- `pages/BootstrapLoginPage.tsx` — `/admin/bootstrap-login` (dev only) calls Cognito `InitiateAuth` (`USER_PASSWORD_AUTH`) with the `admin-bootstrap` client and stores the result as an `oidc-client-ts` `User`. The API's JWT authorizer accepts both clients' audiences ([`infrastructure.md` §6.1](infrastructure.md#61-http-api-apigatewayv2)).

## 7. Pages — behavior detail

### 7.1 HomePage `/`

- Shows only the current group (§4.1), not every membership; the header's group switcher changes which one. Calls `GET /config` (cached) and `GET /groups/{g}/newsletters` for that group.
- Renders the open cycle, then the voting cycle (both exist at once during the response window, [`lifecycle.md` §5.2](lifecycle.md#52-promote_and_opennl)), then the latest published, then up to 3 more past editions.
- Empty state when no memberships: "You haven't joined a group yet — paste your invite code below" with a `<JoinForm/>`.

### 7.2 NewsletterPage `/g/:g/n/:c`

- `useNewsletter` fetches `GET /groups/{g}/newsletters/{c}`.
- Renders one of three layouts:
  - `voting` → redirect to `/g/:g/upcoming` (the candidate UI is the right surface for that state)
  - `open` → list of questions; each row shows: prompt, "your draft" preview if any, status pill (`Not started` / `Draft` / `Published`), CTA → respond
  - `published` → questions list; each question expandable, showing all answers (with images, comments, reactions). Polls show stacked-bar tally with caller's vote highlighted.
- Notes:
  - Every date on a group page is rendered in the group's timezone (`useMembership(groupId).timezone` from `/config`, via `utils/dates.ts#formatInZone` / `cycleLabels`), never the viewer's.
  - The published payload carries no `responseOpenAt`, so the month/year label comes from the cycle's `NewsletterSummary` (`useNewsletters`), falling back to `publishedAt`.
  - Published questions are expanded by default, with a collapse toggle.
  - Comments and reactions render in `AnswerCard` via `CommentList`/`ReactionBar`.
  - An `archived` cycle (410) shows a friendly "archived" state rather than an error.

### 7.3 RespondPage `/g/:g/n/:c/respond/:q`

- For text questions: a markdown editor (textarea with live preview toggle), drag-and-drop image uploader, autosave indicator, Publish button.
  - `useResponseEditor` hook manages in-memory `body` and a **debounced PUT** that fires once the user has stopped typing for `autosaveDebounceMs` (default 1500 ms). It also flushes on `blur` and on `visibilitychange → hidden`.
  - Image upload flow detailed in [`media.md` §3](media.md#3-upload-flow-browser--s3).
- For poll questions: option list with single-select, Publish button.
- Banner showing time-until-deadline (group TZ).
- After publish, page becomes read-only with an "Edit" toggle that reopens editor (until cycle close).
- Notes:
  - Image tokens are inserted as `![alt](image:{imageId})` when an upload turns `ready`. Removing an image strips its tokens and drops its ID, then calls `DELETE /uploads/{id}` behind a permanent-delete `ConfirmDialog` ("This permanently deletes the image. It can't be recovered." — [`media.md` §8.0](media.md#80-explicit-deletion)/§9/§11.4), after the draft without it saves.
  - Publish is disabled while the body is blank with no images, or while an upload is in flight.
  - Editing a published answer autosaves with `publish: false` (publishing is sticky server-side), and the editor says so.
  - A poll selection change on a published poll answer saves immediately.
  - Saves are serialized (one in flight, later edits coalesce). A 409 `CYCLE_NOT_OPEN` stops saving and makes the page read-only. Other 4xx errors stop retrying; only network errors and 5xx retry with backoff.
  - Blur, tab-hide and unmount flush only when `local` differs from the server, so opening a question and leaving does not create an empty draft.
  - The editor doesn't mount until the draft's `imageMediaIds` have been fetched (`GET /uploads/{id}`), because `ImageUploader` reads `initialImages` once. Mounting it empty would autosave the images away. An image that can't be fetched is dropped.
  - A poll pick saves immediately as a draft (`publish:false`), the same as a text autosave. Publish sends `{kind:"poll", pollOptionId, publish:true}`.
- While the caller's answer is a non-empty, unpublished draft, the page shows a persistent note: "Drafts are published automatically when responses close on {date in group tz}. Clear your answer if you don't want it included." ([`lifecycle.md` §8](lifecycle.md#8-race-conditions-and-idempotency), [`engagement.md` §3.6](engagement.md#36-auto-publish-at-close)). `DraftStatusBadge` copy becomes "Draft — publishes automatically at the deadline". The note hides once the cycle has closed; for a poll it shows only the first sentence, because a pick can't be cleared (`SaveResponseRequest.pollOptionId` is required; whether polls need a "clear" action is left open). The badge copy applies only to a settled save of a non-empty unpublished draft; saving, retrying and offline states keep their own copy.
- **Concurrency: last-write-wins.** The server doesn't enforce optimistic-concurrency tokens (see [`api.md` §7.3](api.md#73-put-groupsgroupidnewsletterscycleidquestionsquestionidmy-response)) and the SPA does not implement a conflict-resolution UI. The debounced autosave makes interleaving rare — if a real conflict ever lands, the most recent save wins. We accept this trade for the v1 simplicity it buys; revisit if telemetry shows actual clobbering.

### 7.4 CandidatesPage `/g/:g/upcoming`

- Two sections:
  - "Vote on suggested questions" — list of candidates sorted by votes (default) or recent. Each card: prompt, vote count, upvote button (filled if voted). Disabled when caller is at vote cap; tooltip lists their existing votes with "remove" links.
  - "Suggest a question" — link to `/suggest`.
- Banner: "X days until next newsletter opens" (compute from group settings + clock; group TZ).
- Notes:
  - The cap "tooltip" is an inline, keyboard-reachable panel listing the caller's voted questions with "Remove vote" buttons (a hover-only tooltip isn't accessible).
  - The banner date comes from the `voting` cycle's `responseOpenAt` in `GET /groups/{g}/newsletters`, not recomputed from settings. When an `open` cycle also exists, the page links to it.
  - A `VOTE_CAP_REACHED` 409 shows friendly copy and refetches; the ID list in `detail` is not shown.

### 7.5 SuggestPage

- react-hook-form with `zod` schema:
  ```ts
  z.union([
    z.object({ kind: z.literal("text"), prompt: z.string().min(5).max(500) }),
    z.object({
      kind: z.literal("poll"),
      prompt: z.string().min(5).max(500),
      pollOptions: z.array(z.object({ label: z.string().min(1).max(80) })).min(2).max(6),
    }),
  ]);
  ```
- Submit redirects back to candidates page with a toast.
- The form also has an "Ask anonymously" checkbox (`isAnonymous`, default off) and mirrors the server's trimming and duplicate-label rules. Server `fieldErrors` map onto form fields.

### 7.6 SettingsPage

- Profile card: display name edit, avatar upload (via the dedicated avatar pipeline — `POST /avatars` → poll `GET /avatars/{id}` → `PATCH /me` with the new `avatarMediaId`), and a fallback color picker for users who don't upload one (stored as `avatarColor` on User). Removing an avatar (`DELETE /avatars/{id}`) or replacing it with a new upload permanently deletes the old avatar's image ([`media.md` §11.4](media.md#114-cleanup)) and goes through a `ConfirmDialog` warning it can't be recovered.
- **Notifications**: a master push toggle plus, per group, two independently-toggleable categories — *cycle open* and *deadline reminders*. Publication push is always-on with no toggle; the master toggle and OS-level permission are the only kill-switches.
- **My devices**: push subscriptions with delete buttons + "send test push" action.
- **Your groups**: each group exposes Manage (admins) / View / **Leave**. Leaving the only group where you're the only admin is blocked (server returns `LAST_ADMIN`).
- Session controls (sign out).

### 7.7 GroupAdminPage

Tabs:
- **Members** — list with role pickers, kick buttons (last-admin guarded), member count vs cap.
- **Invites** — generate (with role + TTL), revoke, see status. Display invite as a copyable URL `https://opennewsletter.example.com/join?code=...`.
- **Settings** — `<GroupSettingsForm/>` writing to `PATCH /groups/{g}` (cycle parameters, on-cycle-open default).

There is no Curate tab in v1 — admins do not override voting outcomes. See [`lifecycle.md` §7](lifecycle.md#7-manual-admin-overrides). The admin page has exactly three tabs (Members / Invites / Settings) and the `CurateQuestionsForm` component does not exist.

Notes:
- **Members.** The caller's own row has no actions. Leaving is in Settings → Your groups, and self-demotion is out of scope. Kick goes through `ConfirmDialog`. A 409 `LAST_ADMIN` shows a friendly toast.
- **Invite URL.** Built from the running app as `window.location.origin + import.meta.env.BASE_URL + "join?code=…"` (`utils/inviteUrl.ts`). No hardcoded domain.
- **Invite TTL.** Picked from 1/3/7/14/30/90 days. The default is 7 (`INVITE_DEFAULT_TTL_DAYS`) and 90 is the server max.
- **Expired invites.** The API's `InviteStatus` has no `expired`. The UI derives it as `pending && expiresAt <= now`.
- **Consumed invites.** These show the consumer's `displayName` from `GET /groups/{g}` members, or "a former member" if they've left.
- **Settings form.** One form with an explicit Save, covering name, gradient, timezone, cycle settings, reminder offsets, `onCycleOpen` and `memberSoftCap`. It sends only the changed top-level fields; a changed `cycleSettings`/`notificationSettings` goes as the whole sub-object. On success it invalidates `/config`, because memberships carry the group's name/gradient/timezone. It also invalidates the newsletter list, because a timezone or window change can reschedule the current cycle. Settings apply to the current cycle where possible, not just future ones — see [`lifecycle.md` §6](lifecycle.md#6-settings-changes-mid-cycle) ([D10](../decisions.md#d10)). The form copy reflects this: a line under cycle settings reads "Changes apply to the current cycle where possible." A `responseWindowDays` change that would close an already-`open` cycle in the past is rejected with a 422 whose `fieldErrors` entry is on `responseWindowDays` with code `CLOSES_IN_PAST`. The form recognises it by that code, not by the field name, and surfaces it inline as "Would close the open cycle in the past."

### 7.8 JoinPage `/join?code=...`

If unauthenticated: stash the code in sessionStorage (and in the OIDC `state` data via `login()`) and redirect to login. On `/auth/callback`, after token exchange, the SPA pulls the code back out and navigates to `/join?code=…`, which is now authenticated and redeems it — one redemption code path, not two.

If authenticated: call `POST /invites/redeem` with the code (once, even under StrictMode), then follow [`auth.md` §4.5](auth.md#45-spa-wrapper): set `currentGroup` and navigate to `/g/{groupId}/upcoming`.

## 8. Drafts — detailed flow

### 8.1 Local model

`useResponseEditor` keeps two layers:

- **`server`**: last known `Response` from the server (`body`, `imageMediaIds`, etc. — image captions live on the `ImageMedia` row, not on the response)
- **`local`**: the user's working copy in the textarea

### 8.2 Save loop

1. `local` changes → `dirty = local !== server`
2. After **1500 ms** of no further keystrokes (configurable in `env.ts`), or on `blur`, or on `visibilitychange` to hidden, trigger save.
3. PUT the current local state.
4. On success → `server = response`.
5. **No conflict handling**. The server uses last-write-wins ([`api.md` §7.3](api.md#73-put-groupsgroupidnewsletterscycleidquestionsquestionidmy-response)), so a successful save just becomes the new canonical state. There is no "Use server / Overwrite" UI.
6. **Auto-publish at close.** `lambda-cycle-tick` publishes every non-empty draft when the response window closes ([`lifecycle.md` §8](lifecycle.md#8-race-conditions-and-idempotency), [`engagement.md` §3.6](engagement.md#36-auto-publish-at-close)) — the explicit Publish button still exists ("I'm done"), but an unpublished non-empty draft is no longer lost at the deadline. §7.3 above has the RespondPage warning copy.

### 8.3 Offline / failure

- Save retries with exponential backoff (1s, 2s, 4s, capped at 30s; `retry.ts`).
- The DraftStatusBadge cycles through "Saved a moment ago" / "Saving…" / "Saving failed — retrying" / "You're offline" (via `navigator.onLine`).
- The `local` value (kept in `useResponseEditor`, not a global store) is also mirrored into `localStorage` keyed by `group/cycle/question/userId` so a tab crash doesn't lose work. Cleared after a successful save.

### 8.4 Image uploads in editor

See [`media.md` §3](media.md#3-upload-flow-browser--s3) for the upload protocol. The editor inserts an image-token into the markdown body (`![](image:01HX...)`) and tracks the imageId in `imageMediaIds`. The renderer (`utils/markdown.tsx`, `MarkdownBody`) renders these tokens as `MediaImage`s once the image is `ready` ([`media.md` §7](media.md#7-image-references-in-markdown)). Removing an image also calls `DELETE /uploads/{id}` (real deletion, [`media.md` §8.0](media.md#80-explicit-deletion)) behind a `ConfirmDialog`, after the draft without it saves (§7.3 above).

## 9. Renderers

- Markdown: `react-markdown` + `remark-gfm` for tables/strikethrough/checkboxes. Sanitized via `rehype-sanitize` with a custom schema that allows our `image:` tokens but rejects `<script>`/`<iframe>`/`<style>`/event handlers/`javascript:` URLs.
  - `react-markdown` runs its own `urlTransform` before `rehype-sanitize`, and its default blanks any URL that isn't `http(s)`/`mailto`/etc. `utils/markdown.tsx` therefore passes `image:` through explicitly and defers to `defaultUrlTransform` for everything else.
  - Only `image:{id}` tokens render inline. A remote `![](https://…)` renders as a link, because CSP `img-src` (§12.1) would block it and it would leak readers' IPs to its host.
  - Raw HTML is never parsed (no `rehype-raw`).
- Image rendering uses `<picture>` with `<source srcset>` from `displayUrl` and a `thumbUrl` placeholder for blur-up.
- Polls render as horizontal stacked bars with percentages; caller's pick gets a ring highlight.
- Reactions: pill buttons grouped by emoji with counts. Tap toggles. The `+` button opens `EmojiPickerPopover`: a curated 64-emoji grid plus a native text input for anything else (`emoji-picker-element` was tried and dropped — too heavy for the feature).

## 10. State / data flow

- **TanStack Query** for all server state.
  - Keys are `[entity, ...ids]`, e.g. `["newsletter", groupId, cycleId]`.
  - `staleTime: 30s` for newsletter views, `5m` for group settings, `Infinity` (manual invalidation) for `/config`.
  - Mutations invalidate the smallest reasonable scope (e.g. casting a vote invalidates `["candidates", groupId]` and the leaderboard query).
- **Zustand** for non-server state:
  - `currentGroup` — id of the group the user has selected. Persisted to localStorage.
  - `installPrompt` — the stashed `beforeinstallprompt` event (§14.4).
  - `toast` — toast queue.

## 12. Build & deploy

- `npm run dev` — Vite dev server on `:5173`.
- `npm run build` — outputs `dist/` with hashed assets.
- `npm run preview` — production preview.
- `npm run test` — Vitest.
- `npm run e2e` — Playwright (requires a backend + DDB-local; see [`testing-and-ci.md`](../development/testing-and-ci.md)).

GitHub Pages deploy (see [`testing-and-ci.md` §6](../development/testing-and-ci.md#6-github-actions-workflows) and `.github/workflows/README.md`):
- There is no standalone `frontend-deploy.yml`. One `deploy.yml` auto-deploys the backend to `dev` on every push to `main`; its gated `promote-prod` job (a GitHub Environment `production` with the owner as required reviewer) deploys the backend to `prod` first, then builds and publishes the frontend to `gh-pages` — both from that same commit SHA. GitHub Pages hosts `prod` only; `dev` has no hosted frontend (use `make fe` against it).
- Because backend and frontend promote together from one SHA, backend first, API changes must be **expand → contract** ([`coding-standards.md` §8](../development/coding-standards.md#8-pre-flight-checklist-for-any-code-writing-task)): a route or field is removed only after the frontend release that stops depending on it has shipped, since an installed PWA keeps running its previous frontend until its service worker updates (§5.2 above).
- Vite `base` is `/` since custom domain is at root.
- `404.html` is a copy of `index.html` so SPA deep links work on GitHub Pages.

### 12.1 Content-Security-Policy

GitHub Pages cannot set response headers, so the CSP ships as a `<meta http-equiv="Content-Security-Policy">` tag in `index.html`, generated in code by `src/csp/csp.ts` (pure policy builder, Vitest-tested) and injected by `src/csp/cspPlugin.ts` (`apply: "build"`, so the tag never appears under `vite dev`, which needs `script-src` relaxed for Vite's injected preamble — §13). The plugin reads the `VITE_*` origins via `loadEnv`, reduces each to its origin, and omits any that are empty — HTML `%VITE_*%` substitution would instead leave a literal placeholder for an unset variable.

Policy shape (origins substituted at build time):

```html
<meta http-equiv="Content-Security-Policy" content="
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
  img-src 'self' data: blob: {mediaBaseUrl};
  connect-src 'self' {apiBaseUrl} {uploadOrigins}
    https://cognito-idp.us-east-1.amazonaws.com https://{cognitoHostedDomain};
  font-src 'self' https://fonts.gstatic.com;
  base-uri 'self';
  form-action 'self' https://{cognitoHostedDomain};
  worker-src 'self';
  manifest-src 'self'">
```

Notes:
- `style-src 'unsafe-inline'` is required by Vite-injected styles; accepted trade-off.
- `blob:`/`data:` in `img-src` cover local previews of not-yet-uploaded images.
- `{mediaBaseUrl}` is the one processed-bucket origin every presigned image/avatar URL resolves to ([`media.md` §4.4](media.md#44-spa-usage)). `{uploadOrigins}` in `connect-src` is `VITE_UPLOAD_ORIGINS` (§13) — the two originals buckets' endpoints that `uploadToS3` `PUT`s against directly, space-separated.
- `worker-src`/`manifest-src 'self'` cover the service worker and the PWA manifest.
- Google Fonts origins (`fonts.googleapis.com`/`fonts.gstatic.com`) are needed because `index.html` loads Plus Jakarta Sans and Fraunces from Google. Self-hosting would drop the third-party origins and work offline, at the cost of adding font packages and `woff2` globs to the precache — not done.
- `frame-ancestors` cannot be expressed in a meta CSP — clickjacking protection is out of scope on a GitHub Pages host.
- A Playwright "no CSP violations" test ([`testing-and-ci.md`](../development/testing-and-ci.md)) asserts the meta tag is present and that `img-src` includes the media origin and `connect-src` includes both upload origins.

## 13. Environment variables

`frontend/src/env.ts` parses `import.meta.env`:

```ts
export const env = {
  apiBaseUrl: import.meta.env.VITE_API_BASE_URL,
  mediaBaseUrl: import.meta.env.VITE_MEDIA_BASE_URL,                    // the processed bucket's origin
  uploadOrigins: import.meta.env.VITE_UPLOAD_ORIGINS,                   // space-separated; the two originals buckets' upload endpoints
  cognitoUserPoolId: import.meta.env.VITE_COGNITO_USER_POOL_ID,         // us-east-1_xxxxx
  cognitoClientId: import.meta.env.VITE_COGNITO_CLIENT_ID,              // public frontend client
  cognitoBootstrapClientId: import.meta.env.VITE_COGNITO_BOOTSTRAP_CLIENT_ID, // admin-bootstrap client (dev login only)
  cognitoHostedDomain: import.meta.env.VITE_COGNITO_HOSTED_DOMAIN,
  redirectUri: import.meta.env.VITE_REDIRECT_URI,
  appEnv: import.meta.env.VITE_ENV,                                     // "dev" | "prod"
  buildSha: import.meta.env.VITE_BUILD_SHA,
};

// Authority URL is derived in code so the env file stays minimal:
//   `https://cognito-idp.us-east-1.amazonaws.com/${env.cognitoUserPoolId}`
```

Plus `useMocks: import.meta.env.VITE_USE_MOCKS === "true"`. When set, `AuthProvider` reports a fake signed-in user and `api/client.ts` dispatches to `api/mockTransport.ts` instead of `fetch`. 

Env files:
- `.env.development` is checked in with `VITE_USE_MOCKS=true` and placeholders, so plain `npm run dev` runs fully offline.
- `make fe` runs `vite --mode dev`, which reads the gitignored `.env.dev` that `scripts/write_frontend_env.py` writes from CDK outputs, with `VITE_USE_MOCKS=false`.
- `.env.production` is not yet defined — lands with Milestone 14 ([`build-order.md`](../../plans/build-order.md)).
- `redirectUri` may be empty; the SPA then derives `${origin}/auth/callback`.

The CSP `<meta>` tag from §12.1 applies to production builds only (`cspPlugin`, `apply: "build"`). In dev, `@vitejs/plugin-react` injects an inline preamble script that `script-src 'self'` would block. `.env.e2e` (mock mode, placeholder https origins) is the mode the Playwright `mock` project builds with ([`testing-and-ci.md` §4.3](../development/testing-and-ci.md#43-playwright-e2e)).

## 14. PWA implementation detail

§5 above describes the PWA architecture; this section covers how each piece is actually wired, kept under these headings because code cites them by number.

### 14.1 Plugin + manifest

`VitePWA({ strategies: "injectManifest", srcDir: "src/pwa", filename: "sw.ts", ... })` in [`vite.config.ts`](../../frontend/vite.config.ts), with manifest values from §5.1; `injectManifest` lets our own SW code (§5.4) sit alongside Workbox's precache + runtime caches. Icons live in `frontend/public/` (§2): a monochrome glyph on `theme_color`, with the maskable variant honoring the safe zone (centered ≥80% of canvas). The plugin injects `<link rel="manifest">` into `index.html` automatically.

### 14.2 Service worker

`sw.ts` is registered from [`main.tsx`](../../frontend/src/main.tsx) via `registerSW({ immediate: true })` (`virtual:pwa-register`). It calls `activatePromptly` (`skipWaiting` on install, `clients.claim` on activate) rather than setting `registerType: "autoUpdate"`, because that plugin option's client-side code calls `window.location.reload()` on activation, which would reload a page mid-session. Activating drops the old build's precache, and GitHub Pages stops serving its hashed files, so an open tab could fail to fetch a lazy chunk of the build it's running — the app therefore stays free of `import()`/`React.lazy` chunks entirely (enforced only by convention in `sw.ts`'s comment, not tooling). The SW registers no route for API requests, so `/config` and tokens are always network-only (§5.2).

### 14.3 Web Push subscription wiring

Implemented per §5.3/§5.4; `App.tsx` calls `ensurePushSubscription(vapidPublicKey, { prompt: false })` once the user is loaded, using `config.vapidPublicKey` from `GET /config` ([`notifications.md` §11.2](notifications.md#112-re-subscribe-on-load)). The Settings push toggle calls `ensurePushSubscription` (on) or `pushManager.getSubscription()` + `unsubscribe()` + `POST /push/unsubscribe` (off). Feature-detect: the toggle is hidden entirely when `!('PushManager' in window) || !('Notification' in window)`; iOS Safari gets copy per [`notifications.md` §14](notifications.md#14-failure-modes--ux).

### 14.4 Install prompt

`App.tsx` captures `beforeinstallprompt` and stashes the event in a Zustand store (`src/state/installPrompt.ts`); the UI is `components/pwa/InstallPwaPrompt.tsx`. "Install OpenNewsletter" buttons on Home and Settings call `event.prompt()`, then clear the store on `userChoice` resolution. iOS Safari never fires `beforeinstallprompt`, so iOS user agents instead see a static, dismissible "Add to Home Screen" banner (dismissal persisted in `localStorage`).

### 14.5 GitHub Pages SPA fallback

The `promote-prod` job's frontend-publish step runs `cp dist/index.html dist/404.html` after the Vite build so deep links work — without it, refreshing on `/g/:groupId/n/:cycleId` 404s. Detail: §12.

### 14.6 HTTPS in dev

`pushManager.subscribe`, `Notification.requestPermission`, and the SW lifecycle all require a secure context. `npm run dev:https` runs `vite --mode https` with `@vitejs/plugin-basic-ssl` (self-signed cert); local push testing requires accepting that cert in the browser (documented in [`frontend/README.md`](../../frontend/README.md)). `localhost` itself counts as a secure context, so basic SW work doesn't need HTTPS — only Web Push does.

### 14.7 VAPID keys

The public key flows from `GET /config` at runtime (no `.env` needed for the SPA). Generation and Secrets Manager storage are handled by [`scripts/generate_vapid_keys.py`](../../scripts/generate_vapid_keys.py) per [`notifications.md` §2](notifications.md#2-vapid-keys).

### 14.8 Verification

1. `npm run build && npm run preview` over HTTPS.
2. Chrome DevTools → Application:
   - **Manifest** tab shows all icons + correct theme.
   - **Service Workers** tab shows the SW activated and bypass-for-network-only routes correctly listed.
   - **Storage → Cache Storage** shows the precache populated post-load.
3. Lighthouse PWA audit ≥ 90. Specifically check "Installable", "Configured for a custom splash screen", "Provides a valid `apple-touch-icon`".
4. Force a push: `POST /push/test` with the test push button on Settings; confirm the OS notification fires and clicking it focuses/opens the right URL.
5. Install via Chrome's address-bar install icon and verify the app launches in standalone mode (`display-mode: standalone` in `matchMedia`).

### 14.9 Not built

- Background sync for offline draft saves (Workbox `BackgroundSyncPlugin`). Not built; the current debounced-autosave + localStorage mirror covers tab-crash recovery.
- Periodic background sync for prefetching open cycles. Not built — browser support is Chrome-only and not worth the complexity.
- `share_target` manifest entry to receive shared images from other apps. Not built; see [`future-ideas.md`](../future-ideas.md).

## 14a. Client-derived display data (not API fields)

Several pieces of display state live entirely in the frontend rather than on the API. They are derived from primitive API fields. Keep the derivation in `utils/`, not scattered through components.

- **Month / year labels** (`"June"`, `"2026"`): derived from `responseOpenAt` using the group's `timezone`, which every `/config` membership carries ([`api.md` §2.1](api.md#21-get-config)). Helper: `utils/dates.ts#cycleLabels(responseOpenAt, timezone)`. Never accept a server-supplied label.
- **Word count** on the respond page footer: derived from the local `body` string. Trivial — no helper needed beyond `body.trim().split(/\s+/).length` (zero when empty).
- **Reaction total** on the published-edition header: sum of `reactionGroups[].count` across all answers. Inline in `NewsletterPage.tsx`.
- **"Hype check" banner** — not built; tracked in [`PROGRESS.md`](../../plans/PROGRESS.md). Would be computed from per-user draft counts in the open-newsletter payload. Sketch: a `utils/hype.ts#hypeFor(myPublishedCount, totalQuestions, daysLeft)` helper would return either a string or `null` (suppress when there's nothing motivating to say).
- **`helperText` under recurring questions** (Photo Wall / On Your Mind / Check It Out) — not built; tracked in [`PROGRESS.md`](../../plans/PROGRESS.md). Would be a hard-coded map keyed by prompt slug in `utils/recurring.ts`. The API knows nothing about recurring questions — they're just regular questions that the frontend would recognize by prompt and decorate accordingly.
- **Gradient class** (Tailwind class string, e.g. `bg-gradient-to-br from-violet-500 to-sky-400`): derived from `Group.gradient` / `MembershipSummary.gradient` (a slug like `grape-sky`) via the frontend palette table in `utils/gradient.ts`. The slug is the API contract; the class string is a presentation detail. The allowed slug set is the enum in `shared/openapi.yaml` ([`api.md` §4.3](api.md#43-patch-groupsgroupid)) — the frontend table must cover exactly that set.
- **`avatarColor` → CSS class**: similar — the slug from `User.avatarColor` maps to a Tailwind class in a small frontend table, covering exactly the eight slugs enumerated in [`api.md` §2.3](api.md#23-patch-me).

These fields MUST NOT appear in `frontend/src/types/api.ts` (which mirrors the OpenAPI spec). They live as computed values in component state or as the return type of utility functions.
